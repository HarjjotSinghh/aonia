## 2. What the Muse binary actually does — corrections to the spec

### 2.1 `MUSE_AUTH_PATH` is inert for the binary — **corrects spec**

`strings` over `muse-bin-1.3.0-R3401.1` contains zero occurrences of `MUSE_AUTH_PATH`. Only the
Bash launcher (`~/.local/bin/muse`, lines 19-25) reads it, and only to find a token for
authenticated update downloads (`read_credential()`, lines 486-508); it is never exported to the
binary (`exec "$binary" "$@"` at line 1137 passes only `MUSE_RELEASE_INFO`). A fresh profile with
`MUSE_AUTH_PATH=$HOME/.config/muse/auth.json` still fails with `missing meta credentials`.

The binary resolves its config root as `$XDG_CONFIG_HOME/muse`, else `$HOME/.config/muse`, and
reads `auth.json` from there. Its own bundled skill text says: *"When XDG_CONFIG_HOME is set,
$HOME/.config/muse is outside the active root: never read, list, test-write, or report it as a
fallback."*

**Consequence:** `envFor()` is `{ XDG_CONFIG_HOME, XDG_DATA_HOME }`. Keep `MUSE_AUTH_PATH` only if
we want the launcher's update downloads to authenticate per profile, which is cosmetic. SPEC.md
lines 59 and 121, README.md line 55, and issue #45 all need the three-variable claim removed.
Meta's docs, the SDK issue tracker, `oh-my-musecode/host-reality.md` and `mjolnir` never mention
`MUSE_AUTH_PATH` either.

### 2.2 An empty profile does not inherit the default login — proven

`XDG_CONFIG_HOME=/tmp/aonia-probe/cfg muse exec ...` with no `auth.json` in that root exits 1 with
`missing meta credentials: run \`muse login\` or set META_API_KEY, or save credentials at
/tmp/aonia-probe/cfg/muse/auth.json`. It never touched the network (fake provider saw zero
requests) and never read the Keychain. So config-root isolation is real on macOS too, at the
pointer-file level.

### 2.3 On macOS the pointer file selects one shared Keychain item — the S1 collision, half proven

`~/.config/muse/auth.json` on macOS is 294 bytes, mode 0600, and holds **no token**:

```json
{ "schema_version": 2, "providers": { "meta": {
  "mechanism": "oauth", "storage": "keychain", "obtained_via": "device_code",
  "api_base_url": "https://api.meta.ai/v1", "user_full_name": "...", "user_email": "..." } } }
```

The token is in the login Keychain: one item, service `ai.meta.dev.credentials`, account `meta`.
`security dump-keychain` finds exactly one. Copying that pointer file into a fresh profile root
makes the fresh profile send a real `Authorization: Bearer` (observed against a fake provider,
token never printed). So two profiles whose `auth.json` both say `storage: "keychain"` share one
token. What is *not* yet proven is that a second `muse login` overwrites the item rather than
creating a second one — that is the half of S1 that needs a second account.

### 2.4 `TBH_CREDENTIAL_BACKEND=file` — the likely macOS escape, not yet run end to end

The binary's env-name table contains `TBH_CREDENTIAL_BACKEND`. Disassembly of the gate function
shows it accepts exactly the string `file` (length 4, case-sensitive, untrimmed); every other value
silently falls through to the default keychain-capable provider. Runtime differential: with
`TBH_CREDENTIAL_BACKEND=file` the profile's `.auth.json.lock` is never created; unset or any other
value creates it. The gate runs at process bootstrap for both CLI and TUI.

With `file`, the credential provider has no Keychain handle, so a profile started that way can
never touch `ai.meta.dev.credentials`. The token would then live inline in that profile's
`auth.json` (fields `access_token`, `refresh_token`, `expires_at` exist in the slot schema — the
layout Linux and Windows already use, and the layout the launcher's `read_credential()` parses).

**Not yet done:** a real `muse login` under `TBH_CREDENTIAL_BACKEND=file` in a fresh profile root.
That is safe for the default login (Keychain untouched by construction) but it is a real login and
needs a browser round trip, so it is the first thing to run once a second account exists — or
with the *same* account, since a second login on the same account is enough to prove the write
path. If it works, macOS gets concurrency via a third variable, and S1's escapes (a)/(b) are moot.
Trade-off to state in the README: on macOS the profile token then sits in a 0600 file, same as
Linux and Windows today.

### 2.5 `muse serve` under a profile with no login

It does **not** exit. The MSP handshake completes (`initialize` returns `museHome` = the profile's
data root, `sessionDurability: durable`), `session/start` succeeds and persists a session, and the
first `turn/start` fails ~100 ms later with:

```
turn/completed { terminal: "failed", reason: "not logged in: run /login to add an API key",
                 error: { kind: "authRequired", retryable: false } }
```

stderr stays empty; exit is 0 when the client closes. `usage/read` returns `{}` both logged in and
logged out, so it cannot detect the state. `model/list` can: logged out it returns
`{ source: "bundledCatalog", models: [] }`; logged in it returns `source: "providerCatalog"` with
`muse-spark-1.3`, `muse-spark-1.3-contributor`, `muse-spark-1.2`, `muse-spark-1.2-contributor`.
Helicon already calls `model/list` (`packages/daemon/src/sessions.ts:380`).

Helicon today shows the raw Muse text `not logged in: run /login to add an API key` as the turn
error (`server.ts:2851-2853`) — a TUI slash command Helicon has no equivalent for. Nothing in
`daemon`, `server` or `ui` handles `authRequired`. `classifyServeExit` / `serveExitMessage` in
`packages/daemon/src/mspHost.ts:23-49` are dead code outside their tests.

### 2.6 Other binary facts

- `muse login` has **no flags** ("Log in with your Meta account: approve a code in your browser.
  META_API_KEY always takes priority over the account login."). What it prints to a non-TTY
  stdout/stderr (URL and code, or nothing) is unverified — Helicon's in-app "Add account" depends
  on it. `muse logout` removes the saved credential and leaves `META_API_KEY` alone.
- `muse serve --help`: `--no-session-log`, `--disable-sandbox`, `--sandbox-network`,
  `--disable-write`, `--disable-shell`, `--trust-workspace`. No auth, config-dir or data-dir flag.
- Root flags: `--provider echo|meta`, `--model`, `--reasoning-effort`, `--base-url`. No `whoami`,
  `status`, or `usage` subcommand.
- Data root under 1.3.0: `sessions/YYYY/MM/DD/<uuid>/`, `session-index.db`, `skills/`,
  `plugins/`, `model-catalog/`, `feature-config/`, `runtime/muse/` (unix sockets +
  `.session-registry.mutation.lock`), `tui-history.jsonl`, `local-tracing/`. The runtime dir is
  inside `XDG_DATA_HOME` now, not the uid-keyed `/private/tmp/tbh-<uid>-rt` that
  `host-reality.md` measured for 1.0.x/1.1.x — so S5 contention across profiles is unlikely.
- `muse exec` under a `/tmp` data root warns `unsafe_registry_root ... root component is unsafe or
  unreadable` and disables local session messaging. `~/.aonia/...` should not trigger it; verify
  once profile roots exist.
- Residue outside XDG: `~/Library/Application Support/Muse/session-name-authority/` is resolved
  via `getpwuid`, not `$HOME`, so it is shared across profiles regardless. It holds session naming
  only.
- `muse skills list` still finds `~/.agents/skills` under an isolated root — HOME-based skill
  discovery is independent of XDG, so shared skills need no symlinks.
- `META_API_KEY` string appears 21 times in the binary; the docs say it beats the account login and
  that Muse "tells you" when an env key hides a browser session.
- MSP `clientInfo.name` must match `^[a-z0-9_]+$` (`aonia-probe` was rejected; `helicon` passes).
- `session/contextUsage` is `method not found` on this build; the SDK 0.1.1 warns
  `schemaFingerprintMismatch` and proceeds.
- Installed version equals the channel latest (`.muse-release-info.json`, `muse-stable`,
  `1.3.0-R3401.1`). The launcher self-updates hourly unless `MUSE_NO_AUTO_UPDATE=1`.

## 3. Helicon seams — verified at `27878ba`

### 3.1 Spawn and host keying (`packages/server/src/server.ts`)

- `hostFor(cwd)` (`:2615`) keys hosts by `hostPathFor(cwd) || "__default__"` (`:2621`);
  `hosts: Map<string, ManagedHost>` (`:609`), `starting` (`:610`) dedupes concurrent spawns,
  `sessionHosts: Map<sessionId, hostKey>` (`:616`). `ManagedHost` (`:113-120`) has no account
  field.
- Callers: `GET /api/models` without a session → `hostFor("")` (`:1496`); `startSession`
  (`:2006`); `loadTranscript` (`:2282`); `discover` (`:2401`); the title-upgrade worker (`:2509`);
  `managerForSession` (`:2612`) after a `sessionHosts` miss.
- `serveTargetFor(cwd)` (`:2740`) — POSIX branch (`:2744-2746`) returns `{ command, args, cwd }`
  with **no `env`**, so the child inherits the daemon's environment. Only native Windows sets
  `env` (`{ ...process.env, MUSE_RELEASE_INFO }`, `:2762`). WSL builds `wsl -d <distro> -- ...`
  through `planServe` (`packages/daemon/src/wsl.ts:130-168`) and passes no env.
- `ServeTarget.env` (`packages/daemon/src/mspHost.ts:12`) goes straight to the SDK
  (`mspHost.ts:74`), and the SDK's `spawn()` **replaces** the child env when one is given
  (`@muse-code/sdk/dist/src/connection/spawn.js:363-368`). Any per-profile env must spread
  `process.env` first.
- `forward(hostKey, notification)` (`:2786`) already receives the host key by closure
  (`:2656`), but the `usage/changed` branch (`:2789-2791`) drops it and calls `observeUsage`
  (`:3026`), which folds every host into one `planUsage` field (`:629`) and emits
  `{ type: "plan-usage", usage }` with no key. `GET /api/plan-usage` (`:1313`) returns that one
  value. `SubscriptionUsage` (`sessions.ts:616-621`) has `tier`, `observedAtMs`, `window`,
  `weekly` — no identity.
- Dead host → `hostExited` (`:2681`) → `forgetHost` (`:2696`); respawn is lazy on next `hostFor`.
  `restartHosts` (`:2724`) exists for the sandbox flip and is the pattern for "restart with a new
  profile".
- Session creation: `POST /api/sessions {cwd, approvalMode?, modelId?}` (`:1094`) →
  `startSession` (`:2003`) → `upsertProject` → `hostFor` → `session/start` → `recordSession`
  (records `sandboxDisabled` from `host.target.args`, `:2013-2021`) → `sessionHosts.set`.
- Discovery and resume are per data root: `session/list` and `session/resume` run against the
  host's `XDG_DATA_HOME/muse/sessions`, so `discover()` and `loadTranscript()` must carry the
  account too, not only turns.
- Muse is located purely via PATH on POSIX (`options.musePath ?? "muse"`); the desktop shell
  prepends `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, etc. (`main.rs:297-320`).

### 3.4 Packaging and release

- Workspaces `packages/*`, `apps/*`; engines `node >=22`. `@helicon/server` depends on
  `@helicon/daemon`; daemon depends only on `@muse-code/sdk ^0.1.0` (installed 0.1.1, pure ESM,
  zero deps).
- Desktop bundles the server with esbuild (`apps/desktop/scripts/bundle-server.mjs`): entry
  `packages/server/src/cli.ts`, `platform: "node"`, `format: "cjs"`, **no `external` list** —
  every npm and workspace dependency is inlined into `src-tauri/resources/server.cjs` (only
  `node:*` requires remain). Workspace packages resolve through their built `dist/` (`main`),
  so CI builds daemon/ui/server before `bundle:server` (`.github/workflows/ci.yml:46-51`). An
  `aonia` dependency must therefore (a) be installable under `npm ci` on CI — npm registry, git

  bundle step. Pure TS with only `node:*` imports inlines like the SDK does.
- Sidecar Node is pinned at v22.23.2 (`apps/desktop/scripts/fetch-node.mjs:11`); `node:sqlite`
  works there unflagged. The dev machine runs Node 24 via fnm — not what ships.

## 4. Policy and product facts (Meta docs and terms, fetched 2026-09-21)

- Sign-in: "opens your web browser to approve the session" or paste an API key. The docs never
  say "device code"; `auth.json` records `obtained_via: "device_code"` anyway. Meta Managed
  Accounts cannot use browser sign-in.
- Precedence: "An API key always takes priority over a browser sign-in. Muse Code uses
  `META_API_KEY` if set, then a stored key, and only then a stored browser session."
- Subscription plans: **Everyday** (10-50 prompts per 5 hours), **High** (5×), **Power** (20×).
  Metered in prompts per 5-hour window plus a weekly window. Prices are shown only in onboarding.
- **Contributor vs Standard is a model choice, not an account property** — **corrects spec**.
  `muse-spark-1.3-contributor` is a model id; the docs say the Standard tier covers
  `muse-spark-1.3/1.2/1.1` and the Contributor tier covers the `-contributor` ids. ToS §13.4:
  "The Models you select determine how Meta may use your Content." So the "tier separation"
  motivating case in SPEC §1 and issue #45 does not need two accounts; Helicon's existing model
  picker already does it per project. Drop or reword that case. `tier` in `usage/read` is an
  opaque numeric id; `identityOf()` has no tier at all.
- Terms: §3.1 — keys may not be shared, sold or transferred; no new account to bypass a
  termination. §3.2 — the subscription key "may not be used ... to circumvent your subscription's
  usage limits or billing." Restriction (xii) — no circumventing rate limits or usage quotas.
  Nothing names holding two accounts. The separation positioning is consistent with all of it;
  rotation would not be.
- Entitlement: "The subscription applies to the Muse Code API key that is automatically
  connected in the Muse Code CLI onboarding process." One credential, one subscription.
- SDK repo (`meta-models/muse-code-sdk`): no issue about profiles, keychain or multi-account.
  #9 says `POST /muse-code/key` stopped returning `subs_usage` on 2026-09-11 — relevant to how
  reliable per-account meters will be (see also helicon#26, 5-hour window shows 0%).
- Prior art: `mjolnir` treats Muse as purely XDG-scoped on every OS (its `harness.rs` sets
  `XDG_CONFIG_HOME` to the profile parent and `XDG_DATA_HOME = <home>/.data`); it has no macOS
  Keychain handling for Muse, so it is wrong on this machine. `host-reality.md` (1.0.x-1.1.x)
  confirms only `XDG_CONFIG_HOME`/`XDG_DATA_HOME` are read and lists `MUSE_CONFIG_DIR` as not
  read.

## 5. Decisions to make before M1

1. **`envFor()` contents.** Recommend `{ XDG_CONFIG_HOME, XDG_DATA_HOME }` on Linux/Windows and
   `{ XDG_CONFIG_HOME, XDG_DATA_HOME, TBH_CREDENTIAL_BACKEND: "file" }` on macOS, pending the
   end-to-end login probe in §2.4. Drop `MUSE_AUTH_PATH` from the design, or keep it as a
   launcher-only nicety with a comment saying so.
2. **Profile id.** Make `id` equal the directory slug (validated `^[a-z0-9][a-z0-9-]*$`), so
   `profiles.json` can be rebuilt from directory names and Helicon's `accounts.id` is stable.
   Rename = new slug + move, or disallow rename in v1.
3. **What `tier` means.** Drop `tier` from `aonia list` and from Helicon's `accounts` table.
   Show the subscription plan only if `usage/read` ever exposes a name (today it is a numeric
   id). Contributor/Standard stays on the model picker where it already lives.
4. **Dependency mechanism before npm publish.** Simplest: publish `aonia@0.1.0` to npm first
   (M1 already says so) and depend on it from `@helicon/server` (owner of `serveTargetFor` and
   the REST layer); `@helicon/daemon` gets only the store migrations, no aonia import.
5. **Merge order with PR #46.**
6. **`authRequired` handling in Helicon.** Replace the raw "run /login" text with an account-aware
   message and a button, using `model/list` `source: "bundledCatalog"` as the pre-turn check.
7. **Scaffolding.** ESM (`"type": "module"`, matches the SDK and inlines fine), `node:test`,
   `tsc` build, `engines.node >=22`, `bin: { aonia: "dist/cli.js" }`. None of this is written in
   the repo yet.

## 8. Probe artefacts

`/tmp/aonia-probe/` holds the isolated roots, fake-provider scripts and disassembly dumps from
today; nothing under `~/.config/muse`, `~/.local/share/muse` or the Keychain was modified
(`auth.json` mtime and Keychain `mdat` re-verified afterwards). Six unrelated `muse-bin-1.2.1`
